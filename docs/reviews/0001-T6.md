## Implementer notes
Decisions taken:
- Flow rules live once in `core/validation.py`: `check_flow(flow)` (at least one of from and
  to; from differs from to; not both amount and rate; rate_of only with rate; amount above 0;
  rate above 0 and at most 1 with rate_of present; end_date not before start_date) and
  `check_fires(flow, today)` (one_time on or before today). `set_flow` calls both, `check_fires`
  only when `start_date` or `frequency` is given (R4). The store loader calls `check_flow` in
  place of its two partial checks; a file flow breaking a rule is a shape error naming the flow.
  `check_fires` is not called by the loader: a passed one_time flow in the file is kept (Edge
  cases).
- The `assert` in `core/projection.py` is replaced by `rate_terms(flow) -> (rate, rate_of)`,
  the same function `check_flow` uses for the rate half, so mypy narrows without an assert. A
  hand-built Model with a broken rate flow now raises `ValidationError` in `project`.
- Every core message starts with the argument at fault (`from`, `to`, `amount`, `rate`,
  `rate_of`, `end_date`, `start_date`), so one message serves the tool and the loader.
- `set_flow` operation in `server/operations/flows.py` builds a dict of `Flow` field updates
  from the arguments given: from/to/rate_of resolved through `names.resolve_named` to the
  stored spelling; `amount` alone clears rate and rate_of; `rate` alone clears amount;
  `rate_of` alone keeps the existing rate (retarget) or, on a fixed flow, fails `check_flow`
  with "rate is required with rate_of" (R4). JSON null clears only `from`, `to`, `end_date`;
  null for any other argument is refused by the existing parsers.
- An unknown flow name without `frequency` is an error listing the flow names and saying what
  creates one (mirrors `set_account`, R8). `new_name` on an unknown flow is refused.
- `previous` is built from `Flow` field values compared field by field, mapped to result keys
  (`from_account` -> `from`, `to_account` -> `to`) and taken from the shaped earlier flow
  (Task 0001-T4 carry-forward).
- `similar_flows` is computed on the resulting model: other flows with the same stored from,
  to and frequency; `[]` when none. It is on every `set_flow` result.
- `succeed`, `fail`, `error_text` moved to `tests/helpers.py`; accounts and project tool tests
  import from there.
- Two Task 0001-T3 store tests changed inputs, not intent: the `rate_of` reference case now
  uses a rate flow (a fixed flow with rate_of is refused by the flow rule first), and the
  "neither amount nor rate" case expects the core message ("amount or rate", "rate_of").
- `optional_date` added to `server/operations/arguments.py`; it uses `date.fromisoformat`,
  as the store does.
