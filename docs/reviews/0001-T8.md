Decisions taken:
1. Caps in `core/validation.py`: `MAX_MONEY` (1,000,000,000,000) checked by `check_account`
   (absolute balance) and `check_flow` (fixed amount), so `set_account`, `set_flow` and the loader
   share them. Messages start with the argument and print the limit as "1,000,000,000,000".
2. The R14 check (`check_reportable`) lives in `server/operations/projection.py` beside the
   other project checks, so Spec 0002's `what_if` can reuse it. It runs on the projection that is
   reported (after deflation when `in_todays_money`), before shaping, over every money value:
   row balances and net worth, summary start, end and growth_total, flow totals. Its message
   names horizon_years, growth_rate and the inflation rate (set_inflation_rate).
3. F1 root cause: every write tool now builds its result before `write_model_file` and returns
   it right after; nothing that can fail runs between the save and the result. Not observable at
   S3 without patching internals (shaping cannot fail once caps hold); checked by review.
4. Loader: `UnicodeDecodeError` and `RecursionError` become "not valid JSON: <problem>"; any
   other `OSError` on read (permission, directory, file as parent) becomes "The model file <path>
   cannot be read: <strerror>", naming WHATIF_MODEL_PATH as the fix. `FileNotFoundError` is still
   an empty model.
5. Mode-000 case of AC28 is a `skipif` on euid 0 with reason "root reads a mode 000 file anyway".

Seam questions and flags:

  (task note), such a file never reaches projection: it is a shape error naming the path and

  plan gives.
- Spec 0001 AC27 says the Debt case's amount owed "reaches about 7 x 10^20". Computed:

  test only needs "above 10^15", so it holds either way. Flagged for the spec owner, not changed.
